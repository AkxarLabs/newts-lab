# The agent guide — read the part that applies

`AGENTS.md` is what every agent needs in every session: the lifecycle, the gates, the hard rules. This guide
is the reference it points to — read a section when your work touches it (your procedure's contract or
brief usually says which). Everything here binds exactly as if it were in `AGENTS.md`; it lives here only
so that agents who don't need it don't carry it in every session.

## Target-driven projects (/compete)

**Target-driven projects (`/compete`).** Not every project is a paper. When the task has a **fixed, straightforward target** — a benchmark to beat, a metric to hit, a leaderboard to climb, an internal KPI — `/compete` spins off a project that enters **directly at `active`** and iterates toward the target. It reuses the whole engine (staged scale, frozen eval, budgets, ledger, git, `/experiment`, `/improve`, `/ideate --in-project`, `/research-loop`) and **skips the paper layer**: `/ideate→/lit-review→/scope→/propose` are recorded `N/A (target-driven)` in `IDEA.md` (the `/compete` interview is the Gate-1 compute authorization), there is no novelty gate, and — crucially — **no headline-hypothesis boundary**, so the method space is fully open: model/feature/approach changes and `/ideate --in-project` are all in-bounds, the main way ideas fan out toward the metric. The **frozen set is reinterpreted** as `{the task data/resources, the metric + direction, the output contract, the rules, the deadline}` (`eval_frozen: true` still holds — the metric + local validation split is the frozen eval; selection discipline binds *harder*, since an external scorer **is** the held-out test). Nothing is host-specific — Kaggle is one instance the agent adapts to. The PI-owned brief is `TARGET.md` (machine mirror: `control.yaml` `target:`); close out with `/finalize` (reproducibility pass on the winning run). See the `/compete` skill and `docs/compete.md`.

## In-project iteration: execute and explore

**In-project iteration has two modes** (set by the loop's `LOOP_BRIEF.md` `Mode:`, default `loop.mode: execute`). `execute` runs the approved `PLAN.md` and stops when exhausted. `explore` is the autonomous in-project iterator: when the plan is exhausted with budget left, it may **expand the frontier** (propose results-grounded new experiment lines) and **reopen a non-headline design decision** (`decisions.md` whose `Revisit if:` trigger fired) — re-planning *within* `active` (no new lifecycle state; `active → active`), inside the frozen set and the Gate-2 envelope, capped by `loop.explore_*` and the anti-burn backoff. **Frontier-`expand` is incremental iteration WITHIN the headline hypothesis — it is NOT divergent method-ideation;** generating a genuinely new *approach* to the problem is `/ideate --in-project <slug>` (see Lifecycle's in-project ideation note and the `/ideate` skill). The autonomy boundary is mechanical: reopening a **`Headline: yes`** decision (the central hypothesis the proposal's novelty rests on), touching the frozen set, or exceeding the envelope escalates — a PI note, or under a signed `/autopilot` campaign the same delegation-bounds + overseer `support` check as a Gate-1 self-approval. A `Headline: yes` reopen is not a dead end: it **routes to in-project method-ideation** — `/ideate --in-project <slug>` (under `ideation.in_project_approval`) or a successor hub `/ideate` — never a bare dead-end PI note. Selection discipline (hard rule 5) binds *harder* during exploration: every expanded line still tunes on validation, reports on the frozen test, and needs multi-seed before a paper claim. A pivot is never silent — it lands in `decisions.md`, PLAN.md's Re-planning log, and the bus.

## The back half: analysis, writing, review and back

**Back-half round-trip (`analysis` → `writing` → `internal-review`, and back).** The paper phase runs in a **HUB** session that reads the project's artifacts *across the boundary* (the registry row holds the project path; `runs/`, `claims.yaml` evidence, and figures resolve through it). When `/analyze` or `/review-paper` produces a NEEDS-EXPERIMENT item or a new ablation, route it back to the project as **ONE coordinated cross-repo step**: append the rows to the project's `PLAN.md` (with pre-written criteria) **AND** set the hub registry `state → active` in the *same checkpoint*, then commit the project and emit `replan`. The project may be re-entered **multiple times** across the paper phase — each round is `internal-review/writing/analysis → active → … → writing`, never a new lifecycle state beyond what the lifecycle already names. `/finalize` revisits the project once more for the reproducibility pass (and secures the cited artifacts into the hub).

## In-project method-ideation (/ideate --in-project)

**In-project method-ideation (`/ideate --in-project <slug>`).** The one first-class way to ideate *divergent* new approaches **inside** an active project. It reuses `/ideate`'s generate → fresh-context critic ensemble → tournament → triage, but scoped to **method approaches within the project's FROZEN set** (problem/eval/test/seeds/budgets — never touched; `active → active`, no new lifecycle state). Its output is **candidate approaches, not experiments**, capped by `ideation.in_project_candidates`/`ideation.in_project_rounds`. **Gate discipline:** a surviving approach that would change the **headline hypothesis** must re-enter `/propose` (a mini-proposal — new hypothesis framing + kill-criteria + budget) **or** spawn a successor hub idea (`/ideate`); it **never** enters experiments on a bare PI note — this preserves the `Headline: yes` autonomy boundary, and only a `/propose` re-entry crosses Gate 1. **Two independent PI-owned switches gate it:** the ENABLE flag `ideation.in_project` (a kill-switch — `false` turns the `--in-project` capability OFF, and every router that would reach it must then fall back to a successor hub `/ideate`) and the APPROVAL knob `ideation.in_project_approval` (**campaign-scoped** — it only changes behavior under a signed campaign; manual runs are always PI-gated). **Approval** (`ideation.in_project_approval`): manual/PI-driven runs are PI-gated (surviving candidates queue at `/propose` for human Gate 1); under a signed `/autopilot` campaign the default is auto-approval **within delegation bounds + the overseer `support` check** that already guards autopilot's Gate-1 self-approvals (the campaign brief/config may override to require-PI). Incremental `expand` is unchanged and stays the only autonomous, within-hypothesis generator. Gate 3 is never delegated to an agent: the PI signs it in the dashboard, or — only when the PI's signed campaign brief ticks "Papers may finalize without me" — the executor's campaign keeper records it after re-running the paper audits itself (`tools/gate3.py`).

## Event bus & directives

**Event bus & directives (optional, powers the dashboard).** A file-based, append-only signal stream the optional dashboard reads (`tools/lab_bus.py`; runs append to `lab/.bus/events.jsonl`). It is best-effort and never required — but when you change a registry state, stop at a gate, kill an idea, run a review, or write back, emit a one-line event: `uv run python tools/lab_bus.py emit <kind> [--idea X] [--detail "..."]` (kinds listed in `docs/dashboard.md`). And at every checkpoint — session orientation, each loop/campaign cycle, each experiment attempt, `/advance` selection — run `tools/lab_bus.py inbox`: a PI **directive** there is an instruction to act on within the protocol (it can steer priorities, request runs *within* the envelope, park/kill, answer an open question, stop a loop), then ack it `done` with an evidence pointer. A directive that would touch frozen/PI-owned settings (budgets, evals, gate signatures) is acked `blocked` with the reason — **directives are subordinate to gates and hard rules; a directive is never gate approval.**
  - **Structured commands.** The dashboard can issue a directive carrying `kind:"command"` + an `action` (`start_loop`, `stop_loop`, `set_mode`, `run_smoke`, `request_run`, `prioritize`, `park`, `kill`, `analyze`, `ideate`) and `args` — `inbox` renders these. Execute the action through the normal procedure for it, within the protocol; ack `done`/`blocked` exactly as for a free-text directive. A command is still never gate approval and never overrides a frozen/PI-owned setting. With the executor on, the dashboard ALSO launches the procedure that consumes the command (`run_smoke`/`request_run` → `/experiment`, `start_loop` → `/research-loop`, `analyze`, `ideate`), so the command is in that run's inbox at its first checkpoint.
  - **PI gate signatures from the dashboard.** Because the dashboard binds localhost and is driven by the PI, it can record the PI's **Gate 1, Gate 2 and Gate 3** signatures directly, plus LOOP_BRIEF and campaign authorizations (Gate 1 → a signed marker appended to `proposal.md` — `· envelope approved` when the PI also approved its §5 envelope — plus a `gate1_approved` command; Gate 2 → `gate2_envelope.pi_signed: true` with `signed_via: dashboard:<ts>` in `control.yaml`; Gate 3 → `studies/<slug>/paper/gate3-approval.md` with `signed_via: dashboard:<ts>`, signed behind a typed confirmation). Treat these as the PI signing directly (same authority as the PI editing the file or `/configure`): on a `gate1_approved` command, do the registry transition and proceed to `/spawn-project`; a `signed_via: dashboard:*` envelope is a valid Gate-2 record; a dashboard `gate3-approval.md` is a valid Gate-3 record, and so is one with `signed_via: campaign:lab/campaigns/<f>` while `tools/gate3.py` says that campaign still validly delegates it. **Gate 3 is never delegated to an agent: the PI signs it in the dashboard, or — only when the PI's signed campaign brief ticks "Papers may finalize without me" — the executor's campaign keeper records it after re-running the paper audits itself (`tools/gate3.py`)**; a headless `/finalize` exists only from one of those two records, and an agent never writes `gate3-approval.md`.

## Mechanical guards (tools/guard.py)

**Mechanical guards (`tools/guard.py`).** The highest-risk rules are not only prose — call the guard at the risky transitions and it turns "remember to X" into "can't proceed unless X": `guard.py spawn <slug>` (Gate 1 recorded before `/spawn-project`), `guard.py full-run <slug>` (a signed, unexpired, non-empty Gate-2 envelope before any FULL run; `--reserve` / `release-full-run` book & free concurrent-sweep capacity), `guard.py frozen <slug>` (`eval_frozen` + the PI-owned blocks intact), `guard.py state <slug> <from> <to>` (a legal lifecycle transition *from the row's actual state*), `guard.py append-only <slug>` (the project ledgers were only appended, never rewritten), `guard.py writeback <slug>` (rule 11 done), `guard.py evolve <slug>` (rule 11's triggered operators fired: a kill left a CORRECTION, a results-stage exit left a RECIPE), `guard.py decisions <slug>` (every settled non-headline `decisions.md` decision carries a machine-checkable **Revisit predicate**), `guard.py plan-trace <slug>` (every non-baseline `PLAN.md` row traces to a `D-NNN`/`(expand Rn)` origin; a `Headline-change: yes` row bypassing `/propose` is blocked), `guard.py finalization <slug>` (Gate 3 recorded — a delegated record only while its campaign still delegates it — and refused outright when `AUTOSCIENTIST_NO_GATE3` marks a headless agent that isn't that one /finalize run). Exit **0 = proceed · 1 = blocked · 2 = warn**. A guard **never grants a gate** — it only confirms one is already recorded, or refuses an unsafe move; the PI gates and hard rules still bind exactly as written.

## SYSTEM.md — the machine experiments run on

**SYSTEM.md (optional, PI-owned):** the PI's description of the machine/cluster experiments run on — hardware, data locations, scheduling rules, forbidden actions. Lab default at `lab/SYSTEM.md` (offered by `/setup-lab`; template `templates/SYSTEM.md`), copied into each project at spawn. If present, its constraints bind every agent and subagent like `control.yaml`; agents never edit it. Absent means "no constraints beyond this protocol".

## Traceability hooks

**Traceability hooks (optional, fail-safe).** The lab also runs best-effort traceability hooks (`.claude/settings.json` → `tools/trace_hook.py`) that log each agent/subagent's tool actions to per-worker logs under `.bus/workers/`. They are best-effort and **never block a tool call**; the logs are local/disposable. The harness writes them — agents do not — so the parent-only-ledgers rule (subagent rule 3) is untouched.

## Programmatic agents

**Programmatic agents (optional, PI-owned, OFF by default).** The executor (`tools/executor/`, used by the dashboard and by `tools/executor_cli.py`) runs a procedure — or the PI's free-form instruction — as a **headless top-level session** (claude, or the optional codex / opencode; `agents.programmatic.backend`) in the hub or a project repo: **not a nested subagent**, so it can itself spawn experiment-runner subagents. This is how the lab works several projects at once, coordinated only by the compute-slot ledger and the bus. It is **gated for human oversight**: refused unless the PI set `agents.programmatic.enabled: true`; **depth-capped** (`max_depth`, default 1 — a launched agent can't launch more); each run **inherits every gate** (FULL runs still need a signed `gate2_envelope`; Gate 3 is the PI's, or a signed campaign's through the executor's keeper). **Nothing is lost:** each run has a durable record, its full transcript and bus events under `<bus>/agents/`, and a tracer for every subagent. The PI can **stop** any run live: the dashboard, `executor_cli.py stop`, a bus `kill`/`park` directive, or `compute.max_concurrent_runs: 0` (no new training slots). See `docs/autonomy.md`.

## Headless runs under the executor

**Headless runs under the executor (dashboard "Run a procedure" · `tools/executor_cli.py`).** The same master switch also lets the PI launch any **whitelisted** procedure as a headless session from the dashboard — hub-level (`/propose x`, `/advance`, `/autopilot continue <brief>`, …) or project-level (`/experiment`, `/improve`, `/research-loop`) — each in its own detached supervisor (`tools/executor/`), watched live, paused and resumed on the PI's answers, stoppable — or the PI's own **free-form instruction** ("Ask Newt", skill `ask`). `/finalize` runs only as the one run the PI starts right after signing Gate 3 in the dashboard; every other run has `AUTOSCIENTIST_NO_GATE3` set. **Every headless run carries the signature guard** (`tools/signature_guard.py`, a PreToolUse hook): it denies any write that would create or change a PI signature — gate markers, envelopes, `gate3-approval.md`, LOOP_BRIEF / campaign authorizations, a registry row to `final` without a signed Gate 3, PI-owned config — and the shell escape hatches. Under a PI-signed campaign brief, delegated signatures that name the brief (`via lab/campaigns/<file>`) still work. A denial means: ask the PI. When `NEWTS_RUN_ID` is in your environment you are such a run, and two extra rules bind you: **(1) One question, then stop.** When the procedure needs a PI decision, ask it with ONE `AskUserQuestion` call (concrete options, your recommendation first) as the only tool call in that turn — the run pauses and you are resumed with the PI's answer; a question with no discrete options goes in plain prose as your final message (the PI's reply resumes the session). Backends without `AskUserQuestion`: `lab_bus.py escalate`, state the question, end. **(2) The run footer.** Before ending any turn in which the procedure finished or stopped, emit `lab_bus.py emit run_report --data next="<exact next command, or empty>" --data needs_pi=<none|gate1|gate2|gate3|kill_criteria|null_result|spawn_type|other> --data summary="<≤200 chars>"` (the run id is taken from `NEWTS_RUN_ID`). The footer is how the dashboard knows what you need without parsing prose; a `next` it can launch becomes a one-click button (or, if the PI chose `chain`, the next run — never across a gate). Neither rule relaxes anything above: a question is never a gate, and a directive or an answer never overrides a frozen/PI-owned setting.

## Unattended loops (/research-loop)

- A loop requires a PI-authorized `LOOP_BRIEF.md` before starting — the brief is Gate 2 for the loop; a loop never authorizes itself.
- **Never stop within budget:** while the envelope has budget and no stop condition holds, select an action; FULL work outside the envelope queues as a PI note, the loop continues with other work.
- **Zero-token monitoring:** while a run is in flight, the only check is `scripts/status.py` on the brief's cadence — no log reading or partial-curve reasoning; the run.py watchdog enforces budgets.
- **Anti-burn backoff:** `loop.no_progress_backoff_cycles` consecutive no-progress cycles → stop with a written diagnosis.
- **`explore` mode** (brief `Mode: explore`): when the plan is exhausted with budget left, the loop expands the frontier and reopens non-headline decisions instead of stopping (capped by `loop.explore_*`); reopening a headline decision / touching the frozen set / exceeding the envelope escalates (PI note, or campaign-delegation + overseer check). `execute` (default) stops at plan exhaustion. See "In-project iteration: execute and explore" above and docs/autonomy.md.
- Every cycle appends a Loop Log row; loop exit does the full session write-back (rule 11) plus a PI morning report.
